\section{Introduction}
\label{sec:intro}
% =====================================================================
This report documents Activity 2 of the Weather station system, which extends the MQTT chain of Activity 1 by introducing a LoRa link between two ESP32 boards: a transmitter (TX) node that reads the DHT11 sensor and sends the data over LoRa, and a receiver (RX) node that forwards what it receives to the Mosquitto broker over MQTT, so that the dashboard remains unchanged.

For this activity, two groups joined forces: Aarón Alcalá and Marcos García on one side, and Jaume Pulido and Mikael Rodríguez on the other. The work was split so that each group programmed one of the two nodes. Jaume and Mikael's group developed the TX node, including the handling of the DHT11 sensor, and Aarón and Marcos's group developed the RX node, where the WiFi connection, the MQTT publication to the Mosquitto broker and the web frontend keep the same idea and structure as in Activity 1.

\section{LoRa Configuration}
\label{sec:lora-config}
% ASSIGNED: MIKA
% =====================================================================

The LoRa communication system enables two ESP32-based boards to exchange sensor information wirelessly. The objective is to provide a long-range communication link suitable for IoT applications while keeping the implementation modular and easy to maintain.

The configuration and communication logic are separated into different files. The \texttt{LoRaConfig.h} file defines the radio configuration structure, while \texttt{config.h} contains the default radio parameters and hardware pin assignments. The \texttt{LoRa\_IOT.h} and \texttt{LoRa\_IOT.cpp} files define the communication interface and its implementation. This separation allows the radio parameters to be modified without changing the application logic.

\subsection{Radio Parameters}
\label{sec:lora-params}

The radio configuration is centralised in \texttt{config.h} and passed to the initialisation function through the \texttt{LoRaConfig} structure. The main parameters and their design rationale are described below.

\begin{itemize}
    \item \textbf{Frequency (868 MHz):}
    Selected for operation in the European 868 MHz band, subject to applicable regulations. Both boards must use the same frequency to communicate.

    \item \textbf{Bandwidth (250 kHz):}
    Provides a relatively high data rate compared with narrower bandwidths, making it suitable for transmitting small sensor
    messages periodically.

    \item \textbf{Spreading factor (SF7):}
    Selected to favour a higher data rate and shorter transmission times. This is suitable for small sensor messages, provided that the required communication range and signal quality are maintained.

    \item \textbf{Coding rate (4/5):}
    Adds forward error correction to improve resilience against transmission errors while limiting additional transmission overhead.

    \item \textbf{Sync word (0x12):}
    Helps distinguish our LoRa network from networks using different sync words. Both boards must use the same value.

    \item \textbf{Preamble length (8 symbols):}
    Supports packet detection and synchronisation while limiting transmission overhead.

    \item \textbf{CRC enabled:}
    Allows the receiver to detect corrupted packets and identify transmission errors.
\end{itemize}

The transmit power is also configurable. Its final value must be compatible with the radio module and comply with the applicable regional regulations.

\subsection{Compatibility, Interference and Software Design}
\label{sec:lora-software}

Reliable communication requires both boards to use the same radio parameters (frequency, bandwidth, spreading factor, coding rate and sync word), which is why they are centralised in a single configuration shared by the TX and RX nodes. The sync word reduces the chance of accepting packets from unrelated LoRa networks, but the radio channel is shared, so interference and collisions caused by other devices can still happen. It also provides neither encryption nor sender authentication.

On the software side, the design is modular: the radio configuration is kept apart from the application logic, and the public interface offers initialisation, transmission and reception functions built on top of the Arduino LoRa library. A GPIO interrupt is also configured on the radio so that the arrival of a packet can be signalled to the main program without constant polling (see Section~\ref{sec:rx}). The final parameters should be validated at the expected operating distances and environmental conditions (see Section~\ref{sec:experiments}).

\section{TX node (\texttt{src/tx/main.cpp})}
\label{sec:tx}
% ASSIGNED: JAUME
% =====================================================================

The transmitter is the node placed at the weather station. Its only task is to read the DHT11 sensor periodically and send each reading over LoRa to the receiver, which acts as a gateway towards the MQTT broker. Because it does not need any Internet connectivity, the transmitter does not use WiFi or MQTT at all, which keeps the firmware small and reduces its power consumption.

The program is built with PlatformIO in its own environment (\texttt{env:tx}), which compiles only the \texttt{src/tx/} folder through
\texttt{build\_src\_filter}. The radio code is shared with the receiver and lives in the \texttt{lib/lora} library (\texttt{LoRa\_IOT.h/.cpp}), so the main file only contains the application logic.

\subsection{Configuration}

The radio parameters of the transmitter are the ones described in Section~\ref{sec:lora-params}, loaded from \texttt{include/config.h} into the same \texttt{LoRaConfig} structure used by the receiver. The parameters that are specific to the transmitter are summarised in Table~\ref{tab:lora-config}.

\subsection{Initialisation}

The \texttt{setup()} function opens the serial port for debugging, starts the
DHT11 driver and initialises the radio with \texttt{LoRaIOT\_setup()}:

\begin{lstlisting}[style=arduino, caption={Initialisation of the transmitter.}]
DHT dht(DHT_PIN, DHT_TYPE);
LoRaConfig loraConfig;                  // default values from config.h
int counter = 0;                        // packet id

void setup(){
    Serial.begin(115200);
    dht.begin();

    if (!LoRaIOT_setup(loraConfig))
        while (1);                      // stop if the radio does not answer
}
\end{lstlisting}

\texttt{LoRaIOT\_setup()} starts the SPI bus on the pins of the on-board SX1276, sets the chip-select, reset and DIO0 pins, calls
\texttt{LoRa.begin()} with the carrier frequency and then applies the spreading factor, bandwidth, coding rate, preamble length, sync word and transmission power, and enables the CRC. If the radio does not respond, the function returns \texttt{false} and the program stops, since the node is useless without the radio.

\subsection{Main loop}

Every iteration of \texttt{loop()} performs three steps: it reads the sensor, builds the message and sends it.

\begin{lstlisting}[style=arduino, caption={Main loop of the transmitter.}]
void loop(){
    float temperature = dht.readTemperature();
    float humidity    = dht.readHumidity();

    if (isnan(temperature) || isnan(humidity)) {
        Serial.println("Error leyendo el DHT11");
        delay(2000);
        return;                         // retry without sending anything
    }

    String message = "{\"id\":" + String(counter) + ",\"temperature\":" + String(temperature, 1) + ",\"humidity\":" + String(humidity, 1) + "}";

    if (!LoRaIOT_send(message))
        Serial.println("Error enviando el paquete");

    counter++;
    delay(LORA_SEND_INTERVAL_MS);
}
\end{lstlisting}

\paragraph{Sensor reading.} The DHT11 returns \texttt{NaN} when a reading fails (for example, if it is read too often or a wire is loose). In that case the iteration is discarded and repeated after 2~s, so invalid values are never transmitted.

\paragraph{Message format.} Each reading is encoded as a small JSON object:
\begin{center}
    \texttt{\{"id":12,"temperature":23.4,"humidity":55.0\}}
\end{center}
Values are rounded to one decimal, which matches the resolution of the DHT11. JSON was chosen because the receiver can parse it directly with ArduinoJson and the format is easy to read in the serial monitor. The field \texttt{id} is a counter that increases with every packet; the receiver can use it to detect lost packets by looking for gaps in the sequence. The message is about 43--45~bytes long, far below the 255-byte limit of a LoRa packet.

\paragraph{Transmission.} \texttt{LoRaIOT\_send()} wraps the three calls of the Arduino LoRa library: \texttt{beginPacket()}, \texttt{print()} and \texttt{endPacket()}. The last one is blocking: it returns when the radio signals the end of the transmission (\emph{TxDone}), so when \texttt{LoRaIOT\_send()} returns the packet has already been sent.

\paragraph{Send period.} After each packet the node waits \texttt{LORA\_SEND\_INTERVAL\_MS} (5~s). This respects the DHT11 minimum
sampling period (1~s) and keeps the channel occupancy low: with a time on air of around 44~ms (see Section~\ref{sec:exp-toa}), the duty cycle is below 1\%, which is the limit of the EU868 sub-band used.

\section{RX node}
\label{sec:rx}
% ASSIGNED: MARCOS
% (más adelante se simplificará hacia las partes más básicas)
% =====================================================================

The RX node is the bridge between the LoRa link and the MQTT chain built in Activity 1. Its task is to wait for the packets sent by the TX node, extract the temperature and humidity from them and republish them to the Mosquitto broker, so that the dashboard keeps working exactly as before. The WiFi connection, the MQTT publication and the web frontend follow the same idea and structure as in Activity 1, so the only new element on this node is the LoRa reception.

\subsection{Main program (\texttt{main.cpp})}

The program is built with PlatformIO in its own environment (\texttt{env:rx}), which compiles only the \texttt{src/rx/} folder through \texttt{build\_src\_filter}.

The \texttt{main.cpp} of the RX node reuses the \texttt{WiFiManager} and \texttt{MqttPublisher} classes of Activity 1 and adds the LoRa functions provided by the communication library described in Section~\ref{sec:lora-config}. Besides the WiFi and MQTT objects, the program only needs one extra global variable, \texttt{rxFlag}, a \texttt{volatile bool} that signals that a LoRa packet has arrived.

\paragraph{Initialization.} In \texttt{setup()}, the WiFi manager is started as in Activity 1, and the radio is configured through \texttt{LoRaIOT\_setup(LoRaConfig())}. This is the same call used by the TX node, so both boards share exactly the same radio configuration (frequency, spreading factor, bandwidth, coding rate, preamble length and sync word); otherwise the receiver would not be able to decode the packets. If the radio fails to start, the program stops, since the node would be useless without it. Finally, \texttt{LoRa.receive()} is called to put the radio in continuous receive mode. This call is essential: after \texttt{LoRa.begin()} the module is not listening by default, so without it no packet would ever be detected and the interrupt described below would never fire.

\paragraph{Interrupt-driven reception.} Instead of repeatedly asking the radio whether a packet has arrived, the RX node relies on a hardware interrupt. An interrupt makes the microcontroller run a function only when a given event happens, which here is the arrival of a packet. During \texttt{LoRaIOT\_setup()}, \texttt{attachInterrupt()} associates the DIO0 pin of the LoRa module with the function \texttt{onLoRaRxIRQ()}, which is executed on every rising edge of that pin, i.e.\ when the module signals that a complete packet has been received:

\begin{lstlisting}[style=arduino]
extern volatile bool rxFlag;

void IRAM_ATTR onLoRaRxIRQ()
{
    // The interrupt only signals that a packet has arrived
    rxFlag = true;
}
\end{lstlisting}

The interrupt routine does nothing but raise the flag, since this kind of routine must be as short as possible. The variable is declared \texttt{volatile} in \texttt{main.cpp} because it is modified from the interrupt and read from \texttt{loop()}, so the compiler must not assume that its value stays unchanged between reads. The library file accesses it through \texttt{extern}, and the \texttt{IRAM\_ATTR} attribute keeps the routine in the ESP32 internal RAM so it can run quickly. The heavy work (reading the packet, parsing it and publishing it) is done later in the main loop, outside the interrupt.

\paragraph{Main loop.} On every iteration, \texttt{loop()} follows these steps:

\begin{enumerate}[noitemsep]

    \item The WiFi manager is updated, and the iteration is skipped if there is no connection yet.

    \item If the MQTT connection has not been established, it is attempted again, and \texttt{mqttPublisher.loop()} is called to keep it alive. These steps work exactly as in Activity 1.

    \item If \texttt{rxFlag} is set, it is cleared first and then the packet is read with \texttt{LoRaIOT\_receive()}.

    \item If a packet was read correctly and the MQTT connection is available, the message is handed to \texttt{publishReading()}.

\end{enumerate}

In contrast with Activity 1, the publication is no longer periodic: nothing is sent to the broker until a LoRa message arrives, so the publishing rate is set by the TX node.

\paragraph{Packet reception.} The \texttt{LoRaIOT\_receive()} function checks for an incoming packet using \texttt{LoRa.parsePacket()}. If no packet is available, it returns \texttt{false}. Otherwise, it reads the packet byte by byte using \texttt{LoRa.available()} and \texttt{LoRa.read()}, storing the received data in the \texttt{message} string. It then prints the message and its RSSI value, which indicates the received signal strength. Finally, \texttt{LoRa.receive()} puts the radio back into reception mode, and the function returns \texttt{true} to indicate that a packet has been received.

\paragraph{From the LoRa message to MQTT.} The message received over LoRa is a JSON string. \texttt{publishReading()} deserializes it with \textit{ArduinoJson}, discarding the packet and reporting the error if the parsing fails. Then it extracts only the temperature and the humidity, ignoring the rest of the fields of the received JSON, such as the packet counter \texttt{id}, since that information is not going to be sent over MQTT. Finally, it builds a new JSON with the \texttt{temp} and \texttt{hum} fields through the \texttt{MqttPublisher} and publishes it to the broker:

\begin{lstlisting}[style=arduino]
StaticJsonDocument<200> doc;
DeserializationError error = deserializeJson(doc, message);

if (error) return false;
float temperature = doc["temperature"];
float humidity = doc["humidity"];

publisher.addField("temp", temperature);
publisher.addField("hum", humidity);
publisher.publish(topic, retained);
\end{lstlisting}

Rebuilding the JSON with the same fields as in Activity 1 is what allows the rest of the chain to remain unchanged: the broker and the dashboard receive the same message on \texttt{sensor/1} as if the sensor were connected directly to the node.

\subsection{MQTT}

The MQTT part of the RX node is the same as in Activity 1. The \texttt{WiFiManager} state machine handles the connection to the WiFi network without blocking, and the \texttt{MqttPublisher} class connects to the Mosquitto broker, reconnects automatically if the connection is lost, and serializes and publishes the JSON message. The only difference is that the readings now come from the LoRa packets instead of a local sensor.

\subsection{Frontend}

The frontend does not change either. \texttt{dashboard.py} keeps subscribing to \texttt{sensor/+}, storing the readings in bounded queues and drawing the live charts with Dash and Plotly, as described in Activity 1. Since the RX node publishes the same JSON format and topic, the dashboard cannot tell whether the data comes from a sensor wired to the node or from a remote one over LoRa.

\subsection{Transmission power vs.\ energy consumption and signal strength}
\label{sec:exp-txpower}

The aim of this experiment is to evaluate how the transmission power affects
the signal strength at the receiver and the energy that the transmitter needs
to send each packet. In a battery-powered sensor node there is a trade-off
between both: a higher power gives a stronger and more robust link, but
drains the battery faster.

\subsubsection{Test procedure}

The experiment is automated with a PlatformIO test,
\texttt{test/test\_tx\_power/test\_tx\_power.cpp}, written with the Unity
framework. It runs on the transmitter board and is launched with its own
environment, \texttt{env:tx\_power}, which extends \texttt{env:tx} and only
runs this test:
\begin{center}
    \texttt{pio test -e tx\_power}
\end{center}

The test performs the following steps:
\begin{enumerate}
    \item It initialises the radio with \texttt{LoRaIOT\_setup()} and the same
          configuration as the normal firmware
          (SF\,7, 250~kHz bandwidth, coding rate 4/5, 868~MHz). If this fails, the test fails.
    \item For each power level in $\{2, 5, 8, 11, 14, 17, 20\}$~dBm, it sets
          the power with \texttt{LoRa.setTxPower()} and sends 10 packets,
          500~ms apart. Each packet carries the power used and a sequence
          number, so the receiver can tell which level it belongs to:
          \begin{center}
              \texttt{\{"test":"tx\_power","power":14,"seq":3\}}
          \end{center}
    \item For each packet it measures the time taken by
          \texttt{LoRaIOT\_send()}. Since \texttt{endPacket()} blocks until
          \emph{TxDone}, this is the time on air of the packet plus a small
          SPI overhead.
    \item At the end of each level it prints a CSV line with the power, the
          number of packets sent and failed, and the average time on air, and
          waits 3~s before the next level.
    \item Finally, it restores the default power from \texttt{config.h}. The
          test passes if every packet was transmitted successfully.
\end{enumerate}

The sweep was repeated continuously, so several sweeps were recorded in a
single run. The receiver runs its normal firmware (\texttt{env:rx}) without
any change. For every packet it prints the payload and its RSSI on the serial
monitor, so the RSSI of each power level is obtained from the receiver's log.

The power consumption cannot be measured from the firmware, so the transmitter
was powered from a laboratory power supply at 5~V, and the current shown by
the supply was recorded on video during the sweep. The reading alternates
between a low value while the node is idle between packets and a higher value
while it transmits. The energy spent per packet is then
\begin{equation}
    E_{\text{packet}} = V \cdot I \cdot t_{\text{air}},
    \label{eq:energy}
\end{equation}
where $V = 5$~V is the supply voltage, $I$ the current during the transmission
and $t_{\text{air}}$ the time on air reported by the test. Two values are
given: the energy of the whole board, using the current during the
transmission, and the energy of the radio alone, using the increase over the
idle current, $\Delta I = I_{\text{TX}} - I_{\text{idle}}$.

\paragraph{Setup.} The two Heltec WiFi LoRa 32 V2 boards were placed on a
table in the laboratory, 1~m apart, with line of sight and their antennas
connected.

\subsubsection{Expected behaviour}
\label{sec:exp-toa}

The time on air of a LoRa packet only depends on the spreading factor, the
bandwidth, the coding rate, the preamble and the payload length, not on the
transmission power. With the parameters used (SF\,7, 250~kHz bandwidth, coding rate 4/5 and an
8-symbol preamble), the symbol time is
\begin{equation}
    T_{\text{sym}} = \frac{2^{SF}}{BW} = \frac{2^{7}}{250\,\text{kHz}} = 0.512~\text{ms},
\end{equation}
and, using the formula from the SX1276 datasheet, the 37--38-byte test packets
need 68 payload symbols. Adding the preamble ($8 + 4.25$ symbols), the
expected time on air is about
\begin{equation}
    t_{\text{air}} = (12.25 + 68) \cdot 0.512~\text{ms} \approx 41~\text{ms}.
\end{equation}
For the 43-byte weather messages of the normal firmware it is about 44~ms.
Therefore, the measured time on air should be the same at every power level,
and the energy per packet should change only because of the current drawn by
the power amplifier. The RSSI is expected to grow roughly 1~dB for every dB of
extra transmission power, until the receiver saturates when the boards are
very close.

\subsubsection{Discussion}

\paragraph{Time on air.} The measured time on air was 42.0--42.1~ms at every
power level, as expected, since it does not depend on the transmission power.
It is about 1~ms longer than the theoretical 41~ms of
Section~\ref{sec:exp-toa}. This difference comes from the measurement method:
the time includes writing the payload to the radio over SPI and the delay
until the \emph{TxDone} interrupt is detected.

\paragraph{Signal strength.} The RSSI grows almost linearly with the
transmission power: a linear fit gives a slope of 0.93~dB per dB, very close
to the ideal 1~dB per dB. Going from 2 to 20~dBm raised the mean RSSI from
$-47.4$ to $-30.9$~dBm. The spread between sweeps (standard deviation of
2--4~dB, and up to 10~dB between the means of two sweeps at the same level) is
larger than the spread within a sweep. This suggests small changes in the
environment during the test, such as people moving or the boards being
touched, rather than random noise. No saturation was observed, even at
20~dBm. Practically no packets were lost: the only gaps in the sequence
numbers are at 8 and 17~dBm, not at the lowest power, and the incomplete
first two sweeps are explained by the receiver restart. Even at 2~dBm the RSSI
($-47.4$~dBm) is far above the sensitivity of the SX1276 for SF\,7 and
250~kHz in the 868~MHz band, $-120$~dBm according to its datasheet
(Table~10)~\cite{sx1276}. This is a link margin of more than 70~dB, so at
1~m every power level gives a reliable link.

\paragraph{Energy consumption.} The current during the transmission grows
with the power, from 50~mA at 2~dBm to 65~mA at 20~dBm, while the idle current stays at 42~mA. Since the time on air is constant, the energy per packet
follows the current: the radio alone needs 1.7~mJ per packet at 2~dBm and
4.8~mJ at 20~dBm, about 2.9 times more. Going from 14 to 20~dBm increases it
by 53\% (from 3.2 to 4.8~mJ) for only about 5~dB more signal. For the whole
board the difference is smaller (10.5 to 13.7~mJ), because most of the energy
is consumed by the ESP32, which is active all the time.

These currents should be read as a trend rather than absolute values. A
transmission lasts only 42~ms, which is shorter than the refresh time of the
power supply display, so the value shown is partly averaged with the idle
current. The SX1276 datasheet gives a supply current of 87~mA at
17~dBm and 120~mA at 20~dBm for the radio alone (Table~6)~\cite{sx1276}, clearly higher than the
increase measured here (19 and 23~mA). To measure the real peak current,
the transmitter should send continuously (no pause between packets), or the
current should be measured with an oscilloscope and a shunt resistor.

\paragraph{Trade-off.} At the distance used, even the lowest power gives a
reliable link with a large margin, so increasing the power only spends more
energy without improving the delivery rate. For a battery-powered node, the
best choice is the lowest power that keeps a safe margin at the real
deployment distance. Moreover, in the EU868 band the legal limit is usually
14~dBm ERP, so 17 and 20~dBm were used only for this laboratory test.

\subsection{Bandwidth and data rate}
\label{sec:exp-bw}

The aim of this experiment is to quantify the trade-off between transmission speed and range when the bandwidth and the spreading factor of the link are changed.

\subsubsection{Theoretical background}

LoRa uses chirp spread spectrum modulation: each symbol is a chirp that sweeps the whole bandwidth $BW$ and encodes $SF$ bits. The symbol duration and the nominal bit rate are therefore
\begin{equation}
    T_{\text{sym}} = \frac{2^{SF}}{BW}, \qquad
    R_b = SF \cdot \frac{BW}{2^{SF}} \cdot \frac{4}{4+CR},
    \label{eq:rb}
\end{equation}
where $CR = 1$ for a coding rate of 4/5. Doubling $BW$ halves $T_{\text{sym}}$ and doubles $R_b$, whereas each increment of $SF$ doubles $T_{\text{sym}}$ but adds only one bit per symbol. According to the SX1276 datasheet, the time on air of a packet with a payload of $PL$ bytes, explicit header and CRC is
\begin{align}
    t_{\text{air}} &= \left(n_{\text{pre}} + 4.25 + n_{\text{pl}}\right) T_{\text{sym}}, \label{eq:toa}\\
    n_{\text{pl}} &= 8 + \max\!\left(\left\lceil \frac{8PL - 4SF + 44}{4\,(SF - 2DE)} \right\rceil (CR+4),\; 0\right), \nonumber
\end{align}
where $n_{\text{pre}} = 8$ is the preamble length and $DE = 1$ when the low data rate optimisation (LDRO) is enabled, which the datasheet requires when $T_{\text{sym}} > 16$~ms.

The price of a higher speed is a lower sensitivity, i.e.\ the minimum received power that can still be demodulated:
\begin{equation}
    S = -174 + 10\log_{10}(BW) + NF + SNR_{\min} \quad \text{(dBm)},
    \label{eq:sensitivity}
\end{equation}
where $NF \approx 6$~dB is the noise figure of the receiver and $SNR_{\min}$ is the demodulation limit, which goes from $-7.5$~dB at SF7 to $-20$~dB at SF12. Hence, every SF step improves the sensitivity by about 2.5~dB and halving $BW$ by 3~dB: SF12/125~kHz ($S \approx -137$~dBm) has an advantage of 18.5~dB over SF7/500~kHz ($S \approx -118.5$~dBm), which is roughly 8 times the free-space range. Finally, the 1\,\% duty cycle of the EU868 sub-band forces the node to stay silent for $99\,t_{\text{air}}$ after each packet, so slow configurations also limit how often a reading can be sent.

\paragraph{Hypothesis.} (i) The measured time on air should follow Eq.~\eqref{eq:toa}: it should halve each time $BW$ doubles and grow by about $3.4\times$ from SF7 to SF9 and $6.5$--$7.3\times$ from SF9 to SF12, so SF12/125~kHz should be about 100 times slower than SF7/500~kHz. (ii) The RSSI depends only on the transmission power and the propagation path, so it should be similar for all the configurations, while the SNR should drop by about 3~dB each time $BW$ doubles, since the noise power is proportional to the bandwidth. (iii) At a short distance every configuration should receive all the packets, so the fastest one would be the best choice; the range advantage of a high SF and a narrow $BW$ would only become visible at longer distances.

\subsubsection{Experimental setup}

The experiment uses a dedicated firmware (\texttt{test/range\_speed\_balance\_bw}), flashed on one board as transmitter and on the other as receiver. Both boards sweep the nine combinations of $BW \in \{125, 250, 500\}$~kHz and $SF \in \{7, 9, 12\}$, while the rest of the parameters are those of Table~\ref{tab:lora-config}. Two boards with different configurations cannot communicate, so the change of configuration cannot be negotiated over LoRa. Instead, both boards synchronise their clocks through WiFi and NTP at boot, and each configuration is assigned a time window aligned to the wall clock, so both nodes switch at the same instant without any handshake.

In each window, the transmitter sends 10 packets that contain a sequence number and the transmission timestamp, e.g.\ \texttt{\{"id":3,"t":"18:40:08.650"\}} (27~bytes). The interval between packets is $t_{\text{air}}/0.01$ (minimum 5~s) to respect the 1\,\% duty cycle, so it ranges from 5~s at SF7/500~kHz to 164.7~s at SF12/125~kHz, and a full cycle takes about 57~min. The following metrics are logged:
\begin{itemize}[noitemsep]
    \item \textbf{TX:} measured time on air (duration of the blocking transmission) and its theoretical value from Eq.~\eqref{eq:toa}.
    \item \textbf{RX:} RSSI, SNR and $\Delta t = t_{\text{rx}} - t_{\text{tx}}$ of each packet, and the number of packets received per window.
    \item \textbf{Effective data rate:} $R_{\text{eff}} = 8PL/t_{\text{air}} = 216~\text{bits}/t_{\text{air}}$.
\end{itemize}

The experiment was performed indoors, in a classroom, with each board connected to a separate laptop and placed on different tables about 5~m apart.

\paragraph{Reliability.} All 90 packets were received, so at this distance none of the configurations reached its range limit, and the range side of the trade-off can only be assessed through the SNR margin. Packets from other groups' nodes with the same radio settings were also decoded during the experiment; they were discarded because they did not carry a valid timestamp, which confirms that the sync word does not isolate the network.

\paragraph{Speed.} The measured time on air matches Eq.~\eqref{eq:toa} with a constant overhead of 0.8~ms and follows the expected trends: doubling $BW$ halves it, and the SF7$\to$SF9 and SF9$\to$SF12 steps multiply it by 3.3 and 6.5--7.3, respectively. The effective data rate ranges from 12.3~kbps (SF7/500~kHz) to 0.13~kbps (SF12/125~kHz), a factor of 94, and is about half of $R_b$ because the preamble and the header weigh a lot in a 27-byte packet. The only exception is SF12/250~kHz, measured at 742.2~ms instead of 823.3~ms. Although $T_{\text{sym}} = 16.4$~ms exceeds 16~ms, the Arduino LoRa library computes the symbol duration with an integer division ($1000/(250000/4096) = 16$~ms) and does not enable LDRO; with $DE = 0$, Eq.~\eqref{eq:toa} gives 741.4~ms, which matches the measurement. The link still works because both boards use the same library, but this setting departs from the datasheet recommendation.

\paragraph{Latency.} $\Delta t$ is 11--69~ms longer than $t_{\text{air}}$. Most of this difference does not come from the link but from the offset between the clocks of both boards, which are only synchronised at boot and drift apart by about 0.8~ms/min (13~ppm): for SF9/125~kHz, $\Delta t$ was 283~ms at the start of the session and 238~ms one hour later. The SF12 configurations show an additional delay of about $0.75\,T_{\text{sym}}$ (25, 13 and 6~ms at 125, 250 and 500~kHz), probably due to the demodulation latency of the receiver. Therefore, the time on air measured at the transmitter is the reliable speed metric.

\paragraph{Link quality.} The RSSI stays between $-40$ and $-52$~dBm in all the configurations, without any trend with $BW$ or $SF$, as expected; the variations of a few dB are caused by multipath and people moving around the boards. The reported SNR (5--13~dB) is far below the $\approx 70$~dB expected from the RSSI and the thermal noise floor, which indicates that the SNR estimate of the SX1276 saturates for strong signals. Even so, the 500~kHz configurations show 2.5--4.6~dB less SNR than the 250~kHz ones, consistent with a noise power proportional to $BW$. The margin over the demodulation limit (Figure~\ref{fig:bw-results}d) grows with SF, from 13--18~dB at SF7 to 27--30~dB at SF12, which reflects the larger range of the slow configurations.

\paragraph{Trade-off.} At this distance, SF7/500~kHz is the best option, since it is the fastest and loses no packets. SF7/250~kHz, used by the weather station, doubles the time on air but gains 3~dB of sensitivity, a reasonable balance for a reading every 5~s. The SF12 configurations are only worth it for long links, since the duty cycle limits them to one packet every 37--165~s.

\subsection{Quality of Service: packet loss vs.\ distance}
\label{sec:exp-qos}

The aim of this experiment is to evaluate how the signal strength and the packet delivery degrade as the distance between both nodes increases.

\subsubsection{Theoretical background}

As the radio wave propagates, its power spreads over a larger area and is attenuated by obstacles, so the received power decreases with the distance $d$. This is commonly described by the log-distance path loss model:
\begin{equation}
    RSSI(d) = RSSI(d_0) - 10\,n\log_{10}\frac{d}{d_0} + X_\sigma,
    \label{eq:pathloss}
\end{equation}
where $n$ is the path loss exponent ($n = 2$ in free space and typically 2.7--4 with obstacles) and $X_\sigma$ is a random term of several dB caused by shadowing and multipath fading. A packet can only be decoded while its received power stays above the sensitivity of Eq.~\eqref{eq:sensitivity}, about $-121.5$~dBm for the SF7/250~kHz configuration of the weather station. Close to this limit, the random term makes some packets fall below it, so the packet delivery ratio $PDR = N_{\text{rx}}/N_{\text{tx}}$ drops sharply within a few dB.

\paragraph{Hypothesis.} With a transmission power of 20~dBm, the link budget is about $20 - (-121.5) \approx 141$~dB, whereas the free-space loss at 65~m and 868~MHz is only about 67.5~dB. Between 1 and 65~m, Eq.~\eqref{eq:pathloss} predicts an RSSI drop of 36~dB ($n = 2$) to 54~dB ($n = 3$). Therefore, the RSSI should decrease logarithmically with the distance but remain far above the sensitivity, so no packet loss is expected at these distances unless obstacles add a significant attenuation.

\subsubsection{Experimental setup}

No dedicated firmware was used in this experiment: the boards ran the normal transmitter and receiver firmware (Sections~\ref{sec:tx} and~\ref{sec:rx}) with the configuration of Table~\ref{tab:lora-config}. The receiver was kept at a fixed position, connected to a laptop whose serial monitor logged every received packet together with its RSSI (\texttt{logs/rx\_qos.log}). The transmitter, also connected to a laptop that logged every sent packet (\texttt{logs/tx\_qos.log}), was carried away and stopped at approximately 1, 12, 27, 40, 57 and 65~m, where it kept sending a reading every 5~s. The transmitter was reset at each position, so the incremental \texttt{id} of the messages restarts from 0: lost packets appear as gaps in the received sequence, and comparing both logs gives the number of packets sent and received at each distance.

The experiment was performed indoors, on the third floor of the university building. The receiver was placed next to the bathroom door beside the lift, and the transmitter was moved along the corridor up to the window at its end; the distances are approximate positions along this path. Several doors and columns stood between both nodes, so there was no direct line of sight. Between 8 and 10 packets were sent at each position. An additional measurement was taken about 60~m away and one floor below, at the bottom of a staircase, with several walls in between.

Since the received packets were still about 30~dB above the sensitivity, this loss is more likely due to a deep fade of that single packet or to interference than to the average path loss, although the small number of packets does not allow a statistically significant PDR estimate.

\section{Answers to Guiding Questions}
\label{sec:questions}
% ASSIGNED: MARCOS / MIKA (answers merged)

\begin{enumerate}[label=\textbf{Q\arabic*.}, leftmargin=*]
    \item \textbf{How does LoRa compare to Wi-Fi and Bluetooth in terms of range and power consumption?}

    LoRa offers a much longer range than Wi-Fi and Bluetooth, from hundreds of metres to several kilometres under suitable conditions, while keeping a low average power consumption. The price is a low data rate, so it is only suitable for small messages. Wi-Fi is much faster, but it has a shorter range, needs an access point and generally consumes more energy, while Bluetooth also consumes little but only works at short distances (the exact figures depend on the hardware, the Bluetooth version and the environment). LoRa fits our project because the boards only exchange a small sensor reading every few seconds and no network infrastructure is needed.

    \item \textbf{What are the trade-offs of using lower data rates in LoRa transmission?}

    Lowering the data rate (by increasing the spreading factor or reducing the bandwidth) makes the signal easier for the receiver to detect, which increases the sensitivity and the potential range. The price is a longer time on air: the radio stays on for longer, so each message costs more energy, the shared channel is occupied for longer and the probability of collisions grows, the regulations allow fewer messages per hour and the data arrives with more delay. Therefore, a lower data rate does not necessarily mean a lower consumption. In our case, SF7 with 250~kHz keeps the transmissions short, which is appropriate for small sensor messages as long as the receiver decodes them reliably; a higher spreading factor would only be needed for more range.

    \item \textbf{How does increasing transmission power affect battery life and interference?}

    A higher transmission power improves the received signal strength and can extend the range, but the radio draws more current while transmitting, so the battery lasts less (the consumption does not grow in the same proportion as the radiated power, since it also depends on the efficiency of the radio). It also increases the interference with other devices sharing the same frequencies and, if the boards are very close, it can overload the receiver. The best strategy is therefore to use the minimum power that keeps a reliable link, and the final setting must comply with the radio regulations. In our project, the RSSI measurements and the packet reception of the power experiment (Section~\ref{sec:exp-txpower}) help to find it.
\end{enumerate}
